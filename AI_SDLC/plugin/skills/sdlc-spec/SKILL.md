# sdlc-spec

AI-native SDLC의 2단계(Design)를 담당한다. 원문 프롬프트를 그대로 따른다: 첨부된 intent.md를 읽고,
요구사항과 설계 스펙을 만들고, 이 저장소에서 사용 가능한 skills를 적용해 브랜드/코드 가이드라인에 맞추고,
spec.md에 온전히 문서화한다. 분석가가 스펙을 쓰고 디자이너가 따로 해석하던 두 단계를 한 세션으로 압축하는 것이
이 스킬의 존재 이유다.

## 전제 조건

- `docs/intent/<ticket-id>.md`가 존재하고 사람이 검토·커밋한 상태여야 한다. 없거나 미승인 상태면
  `sdlc-intent`부터 완료하라고 안내하고 멈춘다.

## 절차

1. intent.md를 읽는다. 문제/원하는 결과/영향 범위/제약/미해결 질문을 그대로 근거로 삼는다.
2. **저장소에 있는 skills를 찾아 적용**한다. `.claude/skills/`, 플러그인 skills, `CLAUDE.md`와
   `.claude/CLAUDE.md`에 언급된 컨벤션·브랜드 가이드라인을 확인하고 스펙이 그것과 어긋나지 않게 만든다.
3. `docs/spec/<ticket-id>.md`에 아래 항목을 채운다.

```markdown
# Spec: <티켓 제목> (<ticket-id>)

## 요구사항
<intent의 "원하는 결과"를 검증 가능한 요구사항 목록으로 분해>

## 설계
<접근 방식, 데이터/API 변경, 컴포넌트 구조. 다이어그램은 텍스트로도 가능>

## 적용한 조직 skills/가이드라인
<참고한 skill 이름과 반영한 규칙>

## 정책 충돌
<정책·가이드라인과 충돌하는 지점을 인라인으로 표시. 예: "> ⚠️ 정책 충돌: ...". 충돌이 없으면 "없음">

## 미해결 질문 승계
<intent의 미해결 질문 중 spec 단계에서도 못 푼 것>
```

4. 정책과 충돌하는 부분은 문서 다른 곳에 묻지 말고 **해당 설계 항목 바로 아래 인라인**으로 표시한다.
   나중에 리뷰어가 스펙만 훑어도 충돌 지점을 놓치지 않게 하기 위함이다.
5. spec.md 초안도 intent.md와 동일하게 사람 검토를 거친 뒤 커밋되어야 다음 단계(`sdlc-plan`)로 넘어간다.

## 하지 말 것

- intent.md에 없는 새로운 요구사항을 스펙 단계에서 임의로 추가하지 않는다. 필요하면 "미해결 질문"으로 되돌려
  intent.md를 갱신하도록 요청한다.
- 구현 순서나 파일 단위 작업 목록은 여기서 만들지 않는다. 그건 `sdlc-plan`의 몫이다.
