# sdlc-intent

AI-native SDLC의 1단계(Plan)를 담당한다. 목적은 "위원회가 요구사항을 수집하고 워크숍으로 정제"하던 과정을,
발안자(티켓 작성자, 리포터, 대화 상대)를 짧게 인터뷰해 사람이 읽고 기계가 실행할 수 있는 `intent.md` 한 장으로
압축하는 것이다. 코드를 먼저 만지지 않는다. 이 단계의 산출물은 문서다.

## 입력

- 티켓 본문(제목, 설명, 코멘트, 라벨)
- 관련 에러 로그 또는 스택트레이스 (06 Maintain 단계가 되돌린 경우)
- 발안자와의 대화 스레드

## 절차

1. **입력을 있는 그대로 요약**한다. 없는 내용을 추측해서 채우지 않는다.
2. **발안자를 인터뷰**한다. 다음이 불명확하면 반드시 되묻는다(추측 금지):
   - 지금 무엇이 문제인가 (증상, 재현 경로, 언제부터)
   - 원하는 결과는 무엇인가 (성공을 어떻게 판단하는가)
   - 영향 범위 (어떤 사용자/화면/서비스가 영향을 받는가)
   - 제약 (마감, 건드리면 안 되는 영역, 이미 시도했다가 실패한 접근)
   - 아직 답이 없는 질문 (기술적으로든 정책적으로든)
3. `docs/intent/<ticket-id>.md` (또는 저장소 컨벤션에 맞는 경로)에 아래 형식으로 작성한다.

```markdown
# Intent: <티켓 제목> (<ticket-id>)

## 문제
<지금 무엇이 잘못되었거나 왜 필요한가>

## 원하는 결과
<성공 기준. "어떻게 되면 끝났다고 판단하는가">

## 영향 범위
<파일/모듈/서비스/사용자군>

## 제약
<마감, 건드리면 안 되는 영역, 이전 시도와 실패 이유>

## 미해결 질문
- [ ] <아직 답이 없는 것. 없으면 "없음"이라고 명시>

## 출처
<티켓 URL, 로그 링크, 대화 스레드 등>
```

4. **사람이 검토하기 전에는 다음 단계(spec)로 넘어가지 않는다.** intent.md 초안을 만든 뒤 "이 내용이 맞는지 확인해달라"고
   명시적으로 요청하고, 승인(커밋)이 있어야 `sdlc-spec`으로 넘어간다. 이 검토·커밋 규칙이 실제 가드레일이다 —
   intent.md가 git에 커밋된 상태가 곧 "사람이 승인했다"는 신호다.

## 하지 말 것

- 미해결 질문에 그럴듯한 답을 지어내 채우지 않는다. 모르면 "미해결 질문"에 남긴다.
- 구현 방법(어떤 함수를 고칠지, 어떤 라이브러리를 쓸지)은 여기서 정하지 않는다. 그건 spec/plan의 몫이다.
