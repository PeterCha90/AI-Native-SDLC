# sdlc-maintain

AI-native SDLC의 6단계(Maintain)를 담당한다. 목적은 배포 이후 발생한 장애/회귀를 진단하고, 필요하면 새
티켓을 만들어 01 Plan으로 되돌려 **루프를 닫는 것**이다. 이 스킬은 장애가 실제로 발생했는지 여부를
스스로 판단하지 않는다 — 그건 `ops/detect.sh`의 몫이다.

## 입력

- `ops/detect.sh`가 보고한 σ-tier breach 하나. **이 판정은 결정론적 스크립트가 내리며 모델은 관여하지
  않는다.** 이 스킬은 이미 breach로 판정된 사건을 받아 다음에 뭘 할지만 결정한다.

## Tier별 대응

- **1σ** — 로그만 남긴다. 에이전트가 개입하지 않는다.
- **2σ** — Claude가 **읽기 전용**으로 원인을 진단한다. 코드/설정/인프라 어디에도 쓰지 않는다.
- **3σ** — 에이전트가 행동할 수 있지만, 방법은 둘 중 하나뿐이다: 리뷰 게이트를 거치는 **PR을 여는 것**,
  또는 사전 승인된 runbook을 실행하는 것. **어떤 tier에서도 프로덕션에 직접 손대는 행동은 하지 않는다.**

## 3σ일 때: 루프 닫기

1. 진단 결과를 새 `docs/intent/<new-id>.md`에 **01 Plan 단계와 동일한 형식**으로 작성한다. 형식은
   `sdlc-intent` 스킬의 템플릿을 그대로 따른다 — 여기서 다시 정의하지 않는다.
2. **Linear MCP 커넥터를 통해** 새 티켓을 만든다. 티켓에는 다음을 포함한다:
   - 라벨 `sdlc-auto`
   - 본문에 `sdlc-depth: N+1` 한 줄 (N은 이 breach를 유발한 원인 티켓의 depth)
3. 이 새 티켓이 01 Plan을 다시 트리거하면서 루프가 닫힌다.

## 루프 안전장치

`sdlc-depth`가 설정된 상한을 넘어서게 되면 **새 티켓을 만들지 않는다.** 대신 원인이 된 티켓에 코멘트를
남기고 사람에게 에스컬레이션한다. 자동 티켓 생성이 상한 없이 반복되면 사람이 못 따라가는 루프가 된다 —
깊이 제한은 그걸 막는 마지막 방어선이다.

## 하지 말 것

- breach가 실제로 발생했는지를 모델이 판단하지 않는다. 그 판단은 항상 `ops/detect.sh`가 내린다.
- 어떤 tier에서도 프로덕션에 직접 쓰기/실행하지 않는다. 3σ에서도 반드시 PR 또는 사전 승인된 runbook을
  경유한다.
- 깊이 제한을 넘어선 상태에서 후속 티켓을 만들지 않는다. 그 경우엔 코멘트 + 사람 에스컬레이션이다.
