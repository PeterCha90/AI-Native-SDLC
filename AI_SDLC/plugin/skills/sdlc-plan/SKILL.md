# sdlc-plan

AI-native SDLC의 3단계(Build) 착수 직전을 담당한다. 원문이 강조하는 것은 "plan mode를 기본 시작점으로 삼는다"는
것 — 코드를 먼저 건드리지 않고, 계획을 먼저 세우고, 그 계획을 스스로 심문한 뒤에야 구현에 들어간다.

## 전제 조건

- `docs/spec/<ticket-id>.md`가 존재하고 사람이 검토·커밋한 상태여야 한다. 없으면 `sdlc-spec`부터 안내하고 멈춘다.

## 절차

1. spec.md를 읽는다.
2. `docs/plan/<ticket-id>.md`에 아래 항목을 채운다.

```markdown
# Plan: <티켓 제목> (<ticket-id>)

## 변경할 파일
<경로 목록. 새로 만들 파일과 수정할 파일을 구분>

## 작업 목록 (순서대로)
1. ...
2. ...

## 위험과 제약
<이 변경이 건드리는 공유 코드, 되돌리기 어려운 마이그레이션, 성능/보안에 걸리는 지점>

## 성공 기준
- [ ] lint 통과: <실제 명령>
- [ ] 테스트 통과: <실제 명령>
- [ ] <spec의 요구사항과 1:1로 매핑되는 기준>

## 무엇이 깨질 수 있는가
<아래 "계획 심문" 절차의 결과>
```

3. **계획을 심문한다.** 작업 목록을 다 쓴 뒤, 별도로 아래 질문에 스스로 답하고 "무엇이 깨질 수 있는가" 섹션에 남긴다:
   - 이 변경이 건드리는 코드를 지금 호출하는 다른 곳은 어디인가? 거기도 같이 깨지는가?
   - 동시성/순서를 가정하는 부분이 있는가? (락, 재시도, 이벤트 순서)
   - 롤백이 필요해지면 어떻게 되돌리는가? 마이그레이션처럼 되돌리기 어려운 단계가 있는가?
   - 테스트가 통과해도 놓칠 수 있는 경로는 무엇인가? (에러 경로, 빈 입력, 권한 없는 사용자)
   - 이 작업 목록만 보고 intent.md/spec.md를 한 번도 못 본 다른 엔지니어가 그대로 구현할 수 있는가?
     막히는 지점이 있다면 작업 목록에 그 결정을 명시적으로 추가한다.
4. 심문에서 나온 위험은 "위험과 제약"과 "무엇이 깨질 수 있는가"에 반영하고, 필요하면 작업 목록에
   완화 조치(예: 기존 호출부 테스트 추가, 피처 플래그로 감싸기)를 별도 항목으로 넣는다.
5. plan.md도 사람 검토를 거친 뒤 커밋되어야 실제 구현(코드 편집)에 들어간다.

## 판단 기준

이 plan.md 하나만 읽고, intent.md와 spec.md를 전혀 본 적 없는 다른 엔지니어가 구현을 완료할 수 있어야
"충분히 상세하다"고 본다. 그 기준에 못 미치면 작업 목록이나 위험 섹션을 더 구체화한다.

## 하지 말 것

- 계획 단계에서 실제 코드를 수정하지 않는다. 이 스킬의 산출물은 plan.md뿐이다.
- "무엇이 깨질 수 있는가"를 형식적으로 한 줄만 쓰고 넘어가지 않는다. 최소한 위 질문 각각에 답한다.
