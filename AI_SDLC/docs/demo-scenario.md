# 시연 시나리오

발표자용 대본이다. 굵게 표시한 대사는 그대로 읽어도 되고, 소제목 아래 설명은 진행 순서를 잡기 위한 메모다.

## 0. 사전 준비 체크리스트

시연 시작 20~30분 전에 아래를 모두 확인한다. 관객 앞에서 설치나 로그인을 하지 않는다.

### 미리 띄워둘 것

- 터미널 1개 + 브라우저 1개, 나란히 배치
  - 왼쪽: `runner/` 로컬 데몬 실행 중, Linear webhook 수신 대기 상태 (러너 로그)
  - 오른쪽: 브라우저에 파이프라인 대시보드(`http://localhost:3939/`)를 띄워둔다 — 카드/컬럼/게이트 칩과 06→01 루프가 여기서 실시간으로 보인다
- 브라우저 탭: Linear 워크스페이스, 데모용 보드/프로젝트가 열려 있는 상태. 원 티켓 아래 하위 이슈(게이트 카드) 6개가 트리로 보이는 뷰를 미리 찾아둔다 — 00 setup이 만든 직후 이 화면으로 바로 전환해야 한다. 게이트 카드를 옮길 때 쓰는 탭이므로 대시보드 탭과 별개로 열어둔다.
- 브라우저 탭(예비): 러너 README의 대시보드 미리보기 절차로 띄운 시드 상태 화면 — 러너나 네트워크가 말썽이면 즉시 전환할 수 있게
- `demo/` 프로젝트 로컬 서버: React+Vite 프런트엔드(dev server), FastAPI 백엔드가 둘 다 떠 있는 상태 (04 test의 ego-lite e2e가 이 서버들을 대상으로 돈다)

### 미리 확인/설치해둘 것

- 대시보드 접근 확인: 브라우저에서 `http://localhost:3939/`를 열어 카드 UI가 뜨는지 확인해둔다 (러너 기동 자체는 아래 `curl -s localhost:3939/health` 항목에서 확인)
- ego-lite 온보딩 완료 여부: `printf 'cliLog("ok")\n' | ego-browser nodejs 2>&1` 실행해서 정상 출력 확인 (`cliLog`는 stderr로 나오므로 `2>&1` 필수)
- Claude Code 로그인/인증 상태 — 각 단계가 `claude -p`를 호출하므로 세션 만료 여부 확인
- **Linear MCP 커넥터 인증 상태** — 00 setup(하위 이슈 6개 생성)과 06 maintain의 3σ 경로(신규 티켓 생성)가 `mcp__linear__*` 도구를 직접 호출한다. 대화형 세션에서 `/mcp`로 연결 상태를 확인한다. 인증이 안 돼 있으면 00 setup에서 파이프라인 전체가 "게이트 없이는 못 돈다"는 메시지와 함께 막힌다 — §2의 실패 대비 참고.
- GitHub 인증 상태 — 05 deploy가 PR을 생성함
- 러너 환경변수 **2개**가 셸에 설정되어 있는지 확인. 없으면 러너가 시작 시점에 종료된다.

  ```bash
  export LINEAR_WEBHOOK_SECRET=...   # Linear webhook 설정 화면에서 발급
  export LINEAR_API_KEY=...          # linear.ts 어댑터가 GraphQL(티켓 생성/댓글/게이트 폴링)에 사용 — MCP 인증과는 별개
  ```

  팀 ID는 환경변수가 아니다. `config.ts`에는 `LINEAR_TEAM_ID` 폴백이 없으므로 `runner/sdlc.config.json`의
  `linearTeamId`에 직접 적어야 한다. 이 저장소에는 시연 워크스페이스 값이 이미 채워져 있다
  (`Peter's Place` = `bb9ddb14-778f-49bd-b8e5-429c737eab00`). 다른 워크스페이스로 시연하면
  `mcp__linear__list_teams`로 팀 ID를 새로 조회해 바꾼다.
- 시연 팀의 워크플로 상태에 **Done(`completed`)과 Canceled(`canceled`)가 있는지** 확인한다. 게이트 승인/반려가
  이 두 상태 타입으로만 판정된다. `mcp__linear__list_issue_statuses`로 확인할 수 있다.
- `sdlc-auto` 라벨은 미리 만들어둘 필요가 없다 — 없으면 `resolveLabelIds`가 만든다. 다만 라벨이 정상적으로
  붙는지는 첫 자동 티켓에서 한 번 눈으로 확인한다(라벨이 빠지면 깊이 제한이 작동하지 않는다).

  확인: `node --experimental-strip-types src/index.ts` 를 띄운 뒤 `curl -s localhost:3939/health` 가 `{"status":"ok"}` 를 돌려주면 정상.
- `runner/sdlc.config.json`의 `repoPath`가 `../demo`인지 확인한다 — 파이프라인은 이제 FastCampus 모노레포 루트가 아니라 `AI_SDLC/demo`를 직접 대상으로 한다. `useWorktree: true`이면 03 build가 `.worktrees/<key>/AI_SDLC/demo`(git 최상위 기준 상대 경로를 워크트리 안에서 그대로 재현한 경로)에서 실행된다는 것도 미리 알아둔다.
- **`SDLC_AUTO_APPROVE=1`은 리허설 전용 스위치다.** 이 값을 주면 00 setup과 여섯 게이트를 전부 건너뛴다. 라이브 시연에서는 게이트가 핵심 메시지이므로 **켜지 않는다** — 사전 리허설 녹화나 게이트 이후 구간(04 test 버그, 06 maintain)만 빠르게 확인하고 싶을 때만 켠다.

### 되돌려놓을 상태

- `demo/` 저장소를 클린 브랜치로 리셋한다. 이전 시연에서 남은 PR, git worktree, 로컬 브랜치를 정리한다.
- 데모 프로젝트에 심어둔 버그가 켜져 있는지 확인한다. 버그는 환경변수 하나로 토글된다.

  ```bash
  unset DEMO_STRICT_VALIDATION   # 버그 ON  — POST /todos 가 빈 title 을 그대로 저장한다 (시연 시작 상태)
  export DEMO_STRICT_VALIDATION=1  # 버그 OFF — 빈 title 을 422 로 거부한다 (파이프라인이 고친 뒤의 상태)
  ```

  확인: `AI_SDLC/demo` 에서 `./e2e/check.sh` 를 돌려 **exit 1** 이 나와야 한다. exit 0 이면 버그가 꺼져 있는 것이니 위 `unset` 후 백엔드를 재시작한다(환경변수는 `--reload`가 잡지 못하므로 재시작 필수 — `demo/CLAUDE.md` "반복된 실수" 참고).
- Linear 보드에 이전 시연에서 생긴 게이트 하위 이슈(`[gate] <stage> — 승인자: <role>`)나 자동 생성 티켓(`sdlc-auto` 라벨)이 남아있으면 정리하거나 접어둔다. 새로 생성되는 6장의 게이트 카드와 헷갈리지 않게.

### 네트워크 필요 여부

| 필요 없음 (오프라인 가능) | 필요함 |
| --- | --- |
| 로컬 대시보드(`http://localhost:3939/`) 열람 — 러너가 로컬 프로세스라 오프라인에서도 그려진다 | Linear webhook 수신 (로컬 러너를 외부에 노출해야 함) |
| 러너 README의 대시보드 미리보기 절차로 띄운 시드 상태 화면 | `claude -p` 호출 (API) |
| 슬라이드/발표 자체 | Linear MCP 호출 (00 setup 하위 이슈 생성, 게이트 상태 폴링/댓글, 06의 신규 티켓 생성) |
| | GitHub PR 생성 (05 deploy) |
| | ego-lite e2e 자체는 로컬 서버 대상이라 네트워크 불필요하지만, `claude -p` 단계들과 묶여 있어 전체 파이프라인은 네트워크 의존 |

즉 **Linear→러너 연결, Linear MCP 호출, `claude -p` 호출이 이 시연의 유일한 네트워크 의존 지점**이다. 나머지(대시보드 열람, 로컬 서버)는 오프라인으로도 보여줄 수 있다. 이 구분이 §2 실패 대비의 기준이 된다.

## 1. 시연 흐름 (시간대별)

전체 예상 소요: 약 17~19분 (Q&A 제외). 게이트마다 발표자가 직접 승인자 역할을 맡아 카드를 옮기므로, 이전 버전(게이트 없음, 12~14분)보다 길어졌다 — **이 늘어난 시간 자체가 오늘 메시지다.** 사람이 개입하는 지점이 어디고 몇 번인지를 시간으로 보여준다.

### 1) 도입 — 문제 제기 (1분)

**보여주는 것**: 슬라이드 없이 발표자 얼굴, 또는 원문 인용 슬라이드 한 장.

**대사**:
> **"AI가 코드를 짜는 속도는 이미 사람보다 훨씬 빠릅니다. 그런데 왜 여전히 기획-설계-빌드-테스트-배포-운영까지는 몇 주씩 걸릴까요? 병목이 코드에서 프로세스로 옮겨갔기 때문입니다. 다만 프로세스를 자동화한다고 사람이 완전히 빠지는 건 아닙니다 — 오늘은 사람이 정확히 어디서, 몇 번 개입하는지까지 함께 보여드리겠습니다."**

**소요**: 1분.

### 2) Linear 티켓 생성 → 00 setup — 게이트 6장이 한 번에 생긴다 (2분)

**보여주는 것**: Linear 보드에서 실제로 티켓을 하나 만든다. 왼쪽 터미널(러너 로그)로 전환 → 00 setup이 `mcp__linear__*`로 하위 이슈 6개를 만드는 로그 → Linear 보드를 새로고침해서 원 티켓 아래 6장의 카드(`[gate] 01-plan — 승인자: Product Owner` 등)가 트리로 붙는 것을 보여준다.

**대사**:
> **"지금 Linear에 버그 티켓 하나를 만들겠습니다. 러너가 webhook을 받으면 제일 먼저 하는 일은 코드를 짜는 게 아니라, 이 티켓 아래에 승인 게이트 6개를 하위 이슈로 만드는 겁니다."**
> (Linear 화면 가리키며) **"이 6장이 01 Plan부터 06 Maintain까지 각 단계의 게이트입니다. 카드마다 승인자 역할이 이미 적혀 있죠 — Product Owner, Engineer, Code Owner, Release Manager, Service Owner. 이 6장이 오늘 전체 시연에서 반복해서 돌아올 겁니다."**

**소요**: 2분.

### 3) 01 intent → 게이트 01-plan (1.5~2분)

**보여주는 것**: 오른쪽 브라우저의 대시보드에서 01 intent 칸이 "실행 중"으로 바뀌는 걸 실시간으로 본다. 세션이 끝나면 러너 로그에 "Product Owner 승인 대기" 메시지가 뜨고, 대시보드의 01 intent 아래 게이트 칩도 "승인 대기"로 바뀐다. `docs/intent/<id>.md`가 만들어져 있는 것을 잠깐 연다. Linear로 전환해 `01-plan` 카드를 **Done으로 직접 옮긴다.**

**대사**:
> **"01 intent가 끝나면 러너가 멈춥니다. Product Owner 승인 대기 중이라는 로그가 보이시죠. 지금부터 제가 Product Owner 역할로 이 intent.md를 검토하겠습니다 — 문제, 원하는 결과, 영향 범위가 티켓 의도와 맞는지 봅니다."**
> (Linear에서 카드를 Done으로 옮기며) **"확인했으니 카드를 Done으로 옮깁니다. 매직 커맨드가 아니라 그냥 카드를 옮기는 겁니다 — 러너가 Linear의 워크플로 상태를 폴링하고 있다가 이걸 읽습니다."**

**소요**: 1.5~2분.

### 4) 02 spec → 게이트 02-design (1.5분)

**보여주는 것**: 대시보드에서 활성 단계 하이라이트가 02 spec으로 넘어가는 것, `docs/spec/<id>.md`의 "정책 충돌" 섹션을 짧게 보여준 뒤 `02-design` 카드를 Done으로 옮긴다.

**대사**:
> **"02 spec도 같은 Product Owner가 봅니다. 여기서 중요한 건 '정책 충돌' 섹션이에요 — 스펙이 조직 정책과 부딪히는 지점을 숨기지 않고 바로 옆에 표시하게 만들었습니다. 이걸 보고 승인 여부를 판단합니다."**

**소요**: 1.5분.

### 5) 03 plan → 게이트 03-build — 코드는 아직 한 줄도 안 바뀐다 (2분)

**보여주는 것**: `docs/plan/<id>.md`를 열어 "변경할 파일", "작업 목록", 특히 "무엇이 깨질 수 있는가" 섹션을 가리킨다. `git status`로 코드가 전혀 바뀌지 않았음을 보여준 뒤, 역할을 Engineer로 바꿔 `03-build` 카드를 Done으로 옮긴다.

**대사**:
> **"03 단계는 게이트를 사이에 두고 계획과 구현으로 쪼개져 있습니다. 지금 보시는 plan.md는 계획 단계 산출물이고, 이 시점까지 코드는 한 줄도 안 바뀌었습니다 — `git status`가 깨끗하죠."**
> **"이번엔 Engineer 역할로 승인합니다. 제가 보는 건 '무엇이 깨질 수 있는가' 섹션이에요 — 이 변경을 지금 호출하는 다른 코드가 있는지, 롤백은 어떻게 하는지 에이전트 스스로 심문한 결과입니다. 이게 괜찮아야 실제 코드 편집이 시작됩니다."** (카드를 Done으로 옮긴다)

**소요**: 2분.

### 6) 03 build, 04 test — 코드가 쌓이고 심어둔 버그가 e2e에 걸림 (3분)

**보여주는 것**: 승인 직후 03 build가 git worktree 안에서 코드를 짜는 것(대시보드의 03 build 칸 또는 `git log`/`git diff`), 04 test가 이어서 자동으로 도는 것. pytest/vitest는 통과하지만 ego-lite e2e에서 실패하는 로그.

**대사**:
> **"승인이 나야만 03 build가 코드를 편집합니다. 여기서 CLAUDE.md, skills, hooks 3층 가드레일이 걸립니다 — 보호된 경로를 건드리거나, plan.md에 없는 파일을 커밋하려 하면 hook이 그 자리에서 막습니다."**
> **"04 test로 넘어가면 이 데모 프로젝트에 일부러 심어둔 버그가 걸립니다. 단위 테스트는 통과하지만, 실제 화면에서는 값이 어긋나는 정도의 버그라 ego-lite가 실제 브라우저 스냅샷으로만 잡아냅니다."**

**소요**: 3분(로그가 뜰 때까지 대기 포함).

### 7) 게이트 04-test — 실패를 사람이 확인한다 (1.5분)

**보여주는 것**: 실패 요약(단위/e2e 결과)이 `04-test` 카드에 코멘트로 먼저 붙는 것을 보여준 뒤, 역할을 Code Owner로 바꿔 카드를 Done으로 옮긴다.

**대사**:
> **"이번엔 Code Owner입니다. 이 게이트를 승인한다고 배포가 되는 게 아닙니다 — 04 test가 실패했다는 판단 자체를 사람이 확인했다는 뜻입니다. 실패했으니 05 deploy는 건너뛰고 바로 06 maintain으로 넘어갑니다."**

**소요**: 1.5분.

### 8) 06 maintain — 결정론적 감지, 그리고 Linear에 새 티켓 자동 생성 (클라이맥스, 2분)

**보여주는 것**: `ops/detect.sh`가 e2e 실패를 받아 `tier=3 action=act`를 출력하는 로그(모델 호출이 전혀 없는 순수 스크립트라는 점을 강조) → `sdlc-maintain` 스킬이 원인을 진단하고 `docs/intent/`에 새 intent.md를 쓰는 것 → Linear MCP로 새 티켓을 만드는 순간. Linear 보드를 다시 띄워 새 카드가 뜨는 걸 실시간으로 보여준다.

**대사**:
> **"여기가 오늘 보여드리고 싶었던 핵심입니다. '이상이 발생했는가'는 모델이 판단하지 않습니다. `ops/detect.sh`라는 순수 스크립트가 baseline과 sigma로 계산합니다 — 지금 로그에 tier=3이 찍혔죠. 이 tier가 3 이상일 때만, 그것도 사후에 Claude가 진단과 티켓 작성 역할로 불려옵니다."**
> (Linear 화면 가리키며) **"지금 막 생긴 이 카드가 그겁니다. `sdlc-auto` 라벨과 depth 값이 붙어서 자동 생성된 티켓이라는 걸 구분할 수 있습니다."**

**소요**: 2분. **이 구간은 절대 서두르지 않는다** — 발표의 핵심 메시지가 여기서 완성된다.

### 9) 게이트 06-maintain — 마지막 카드도 사람이 닫는다 (1분)

**보여주는 것**: `06-maintain` 카드에도 진단 요약이 코멘트로 붙어 있는 것을 보여주고, Service Owner 역할로 Done으로 옮긴다. 이제 Linear 보드에 6장의 게이트 카드가 전부 Done으로 보인다.

**대사**:

> (보드 전체를 가리키며) **"6장 전부 Done입니다. 오늘 자동으로 도는 걸 보여드렸지만, 실제로는 6번 사람이 판단했습니다."**

**소요**: 1분.

### 10) 새 티켓이 01을 재트리거 — 루프가 닫힘 (1분)

**보여주는 것**: 방금 생긴 티켓이 다시 러너로 들어와 00 setup부터(새 게이트 6장 생성) 다시 시작되는 것을 로그로 짧게 확인. 대시보드에서도 원래 카드에 "↺ 06 → 새 티켓 → 01" 표시가 붙고, 그 링크를 눌러 새로 생긴 카드로 넘어가는 걸 보여준다.

**대사**:

**소요**: 1분.

## 3. 질의응답 대비

| 예상 질문 | 답변 요지 |
| --- | --- |
| **왜 게이트마다 사람이 필요한가?** | 파이프라인이 자동으로 도는 것과 자동으로 승인되는 것은 다른 문제이기 때문이다. 각 단계 산출물은 다음 단계로 넘어가기 전에 그 산출물의 소유자(Product Owner/Engineer/Code Owner/Release Manager/Service Owner)가 판단해야 하는 지점이 있다 — 특히 03 build 직전(코드를 실제로 건드리기 전)과 05 deploy(프로덕션에 영향), 06 maintain(자동 티켓이 계속 루프를 돌릴지)이 그렇다. 게이트가 없으면 6단계 전체가 사람 관여 없이 끝까지 도는데, 그건 이 설계가 막으려는 정확히 그 상황이다 — 게이트 맵이 없으면 러너가 아예 시작하지 않는 것도 같은 이유다. |
| **승인을 기다리는 동안 무엇을 보여주나?** | 대기 자체를 침묵으로 채우지 않는다. 게이트 하위 이슈에는 그 단계 산출물 요약(문서 경로, 테스트 결과, PR diff 등)이 코멘트로 먼저 붙으므로 그걸 화면에 띄워 놓고 설명을 이어간다. 라이브 시연에서는 발표자가 그 자리에서 바로 승인자 역할로 카드를 옮기기 때문에 대기 시간은 수 초~수십 초로 짧다. 실제 대기가 길어지는 상황(다른 사람이 승인해야 하는 경우)을 보여주고 싶다면 미리 녹화한 세션으로 건너뛴다. |
| 에이전트가 프로덕션에 직접 배포하나? | 아니다. 05 deploy는 PR 생성과 리뷰 게이트까지다. 실제 프로덕션 배포·인프라는 이 설계의 범위 밖이고, `RELEASE_APPROVED=1` 없이는 `production-gate.sh`가 그 이후 어떤 배포 명령도 막는다. |
| 비용은 얼마나 드나? | 단계마다 `claude -p` 세션 비용이 들지만, 원문 기준 build 단계에서만 2배 속도 향상이 보고됐고 사람 리뷰/워크숍 비용이 줄어드는 걸로 상쇄를 노린다. 정확한 금액은 사용량과 모델 선택에 따라 달라 여기서 고정 수치를 제시하진 않는다. |
| 에이전트가 잘못된 코드를 밀면 어떻게 막나? | hooks가 결정론적으로 막는다 — 보호 경로 편집 차단(`guard-protected-paths`), 자격 증명 diff 차단(`block-secrets`), plan.md에 없는 파일 커밋 차단(`plan-drift`), 버그 수정 중 테스트 파일 편집 차단(`protect-tests`), 성공 기준을 실행하지 않은 완료 선언 차단(`verify-before-done`), 에이전트 설정 변경 후 테스트 스위트 실행(`config-eval`), 그리고 05 deploy의 `production-gate`는 `RELEASE_APPROVED=1` 없이는 그 자리에서 막는다. CLAUDE.md/skills는 유도일 뿐이고 hooks만 강제한다. 그리고 그 이전에, 코드가 바뀌기 시작하는 시점 자체가 03-build 게이트를 사람이 승인해야만 열린다. |
| 이미 Jira를 쓰는데 Linear로 갈아타야 하나? | 아니다. 트리거 소스는 `TicketSource` 인터페이스(`verify`/`parse`/`createTicket`/`comment`/`createSubIssue`/`getStateType`/`listComments`) 하나로 격리돼 있다. `adapters/jira.ts`가 이 인터페이스만 구현하면 드롭인 교체다. 이번 데모는 구현체로 Linear를 썼을 뿐이다. |
| 무한 루프에 안 빠지나? | 두 겹으로 막는다. 먼저 `ops/detect.sh`가 결정론적으로 이상 여부를 판정하고(1σ=로그만, 2σ=진단만, 3σ만 티켓 생성 후보), 그다음 06이 만드는 티켓엔 `sdlc-auto` 라벨과 depth 값이 붙는다. depth가 상한을 넘으면 3σ여도 자동 재생성을 멈추고 사람에게 에스컬레이션한다. |
| GitHub Actions를 안 쓰는 이유는? | 실행기를 로컬 러너 하나로 뒀다. CI 러너에서는 대시보드를 실시간으로 띄워 보여주는 게 어렵고, 애초에 요구사항에 CI가 없었다. |
| 대시보드가 죽으면 파이프라인도 멈추나? | 아니다. 대시보드는 `runner/.state/`를 읽기만 하는 뷰어(`GET /api/runs`)라서, 대시보드가 응답하지 않아도 러너의 단계 실행·게이트 판정 자체는 영향받지 않는다. 다만 진행 상황을 보여줄 화면이 없어지므로, `curl -s localhost:3939/health`로 먼저 러너 생존을 확인하고 필요하면 왼쪽 터미널 로그만으로 이어간다. |
