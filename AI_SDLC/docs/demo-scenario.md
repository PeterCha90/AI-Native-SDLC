# 시연 시나리오

발표자용 대본이다. 굵게 표시한 대사는 그대로 읽어도 되고, 소제목 아래 설명은 진행 순서를 잡기 위한 메모다.

## 0. 사전 준비 체크리스트

시연 시작 20~30분 전에 아래를 모두 확인한다. 관객 앞에서 설치나 로그인을 하지 않는다.

### 미리 띄워둘 것

- 터미널 2개, 나란히 배치 (`zoetrope.md` §4 화면 배치 참조)
  - 왼쪽: `runner/` 로컬 데몬 실행 중, Linear webhook 수신 대기 상태
  - 오른쪽: `zoe` 실행 준비된 셸 (아직 실행은 안 해도 됨)
- 브라우저 탭: Linear 워크스페이스, 데모용 보드/프로젝트가 열려 있는 상태
- 브라우저 탭(예비): https://zoetrope.furkankly.dev/app — CLI가 말썽이면 즉시 전환할 수 있게
- `demo/` 프로젝트 로컬 서버: React+Vite 프런트엔드(dev server), FastAPI 백엔드가 둘 다 떠 있는 상태 (04 test의 ego-lite e2e가 이 서버들을 대상으로 돈다)

### 미리 확인/설치해둘 것

- `zoe` CLI 설치 확인 (`brew install furkankly/tap/zoetrope` 또는 `cargo install zoetrope`)
- ego-lite 온보딩 완료 여부: `printf 'cliLog("ok")\n' | ego-browser nodejs 2>&1` 실행해서 정상 출력 확인 (`cliLog`는 stderr로 나오므로 `2>&1` 필수)
- Claude Code 로그인/인증 상태 — 각 단계가 `claude -p`를 호출하므로 세션 만료 여부 확인
- GitHub 인증 상태 — 05 deploy가 PR을 생성함
- 러너 환경변수 3개가 셸에 설정되어 있는지 확인. 없으면 러너가 시작 시점에 종료된다.

  ```bash
  export LINEAR_WEBHOOK_SECRET=...   # Linear webhook 설정 화면에서 발급
  export LINEAR_API_KEY=...          # 06 단계가 티켓을 만들 때 사용
  export LINEAR_TEAM_ID=...          # runner/sdlc.config.json 의 linearTeamId 로도 지정 가능
  ```

  확인: `node --experimental-strip-types src/index.ts` 를 띄운 뒤 `curl -s localhost:3939/health` 가 `{"status":"ok"}` 를 돌려주면 정상.

### 되돌려놓을 상태

- `demo/` 저장소를 클린 브랜치로 리셋한다. 이전 시연에서 남은 PR, git worktree, 로컬 브랜치를 정리한다.
- 데모 프로젝트에 심어둔 버그가 켜져 있는지 확인한다. 버그는 환경변수 하나로 토글된다.

  ```bash
  unset DEMO_STRICT_VALIDATION   # 버그 ON  — POST /todos 가 빈 title 을 그대로 저장한다 (시연 시작 상태)
  export DEMO_STRICT_VALIDATION=1  # 버그 OFF — 빈 title 을 422 로 거부한다 (파이프라인이 고친 뒤의 상태)
  ```

  확인: `AI_SDLC/demo` 에서 `./e2e/check.sh` 를 돌려 **exit 1** 이 나와야 한다. exit 0 이면 버그가 꺼져 있는 것이니 위 `unset` 후 백엔드를 재시작한다.
- Linear 보드에 이전 시연에서 생긴 자동 생성 티켓(`sdlc-auto` 라벨)이 남아있으면 정리하거나 접어둔다. 새로 생성되는 티켓과 헷갈리지 않게.

### 네트워크 필요 여부

| 필요 없음 (오프라인 가능) | 필요함 |
| --- | --- |
| `zoe <file.jsonl>` 로 이미 만들어둔 세션 재생 | Linear webhook 수신 (로컬 러너를 외부에 노출해야 함) |
| `zoe inspect <file.jsonl>` | `claude -p` 호출 (API) |
| 슬라이드/발표 자체 | GitHub PR 생성 (05 deploy) |
| | ego-lite e2e 자체는 로컬 서버 대상이라 네트워크 불필요하지만, `claude -p` 단계들과 묶여 있어 전체 파이프라인은 네트워크 의존 |

즉 **Linear→러너 연결과 `claude -p` 호출이 이 시연의 유일한 네트워크 의존 지점**이다. 나머지(zoe 재생, 로컬 서버)는 오프라인으로도 보여줄 수 있다. 이 구분이 §3 실패 대비의 기준이 된다.

## 1. 시연 흐름 (시간대별)

전체 예상 소요: 약 12~14분 (Q&A 제외).

### 1) 도입 — 문제 제기 (1분)

**보여주는 것**: 슬라이드 없이 발표자 얼굴, 또는 원문 인용 슬라이드 한 장.

**화면**: (슬라이드를 쓴다면) "코드는 더 이상 병목이 아니다" 문구.

**대사**:
> **"AI가 코드를 짜는 속도는 이미 사람보다 훨씬 빠릅니다. 그런데 왜 여전히 기획-설계-빌드-테스트-배포-운영까지는 몇 주씩 걸릴까요? 병목이 코드에서 프로세스로 옮겨갔기 때문입니다. 오늘은 이 프로세스 자체를 자동화한 파이프라인을 직접 돌려보겠습니다."**

**소요**: 1분.

### 2) Linear 티켓 생성 → 러너 로그 (1~2분)

**보여주는 것**: Linear 보드에서 실제로 티켓을 하나 만든다. 왼쪽 터미널(러너 로그)로 전환.

**화면**: Linear에 티켓 카드 생성 → 왼쪽 터미널에 webhook 수신 로그가 찍히는 것.

**대사**:
> **"지금 Linear에 버그 티켓 하나를 만들겠습니다. 별도로 아무것도 안 눌러도, 로컬에서 돌고 있는 러너가 이 webhook을 받아서 바로 파이프라인을 시작합니다."**
> (터미널 로그 가리키며) **"여기 보시면 티켓 ID를 받아서 01 intent 단계를 시작한다는 로그가 찍힙니다."**

**소요**: 1~2분(티켓 작성 + 로그 확인).

### 3) zoe 화면 — 01 intent 실시간 (1~2분)

**보여주는 것**: 오른쪽 터미널에서 `zoe --follow`(또는 방금 생성된 세션 파일 지정)로 전환.

**화면**: 01 intent 세션이 zoe 그래프 위에서 실시간으로 진행되는 모습 — 세션 트리에 노드가 붙는 것.

**대사**:
> **"이건 zoetrope라는 뷰어인데, 원래 Claude Code 세션을 리플레이하려고 만든 도구입니다. 저희는 파이프라인의 각 단계를 실제 `claude -p` 세션으로 돌리기 때문에, 이 도구를 그대로 가져다 쓸 수 있었어요. 별도 시각화 코드를 짤 필요가 없었습니다."**
> **"지금 도는 게 01 intent 단계입니다. Linear 티켓 본문을 읽고 `docs/intent/<id>.md`를 만들고 있습니다."**

**소요**: 1~2분.

### 4) 02 spec, 03 build — 아티팩트가 쌓이는 것 (2~3분)

**보여주는 것**: zoe 화면이 다음 세션으로 넘어가는 것(01→02→03), 동시에 편집기나 `git log`/`git diff`로 실제 파일이 생기는 걸 잠깐 보여준다.

**화면**: zoe에서 새 세션 노드, 파일 탐색기 또는 터미널에서 `docs/spec/<id>.md`, `plan.md`, 코드 diff가 순서대로 생기는 것.

**대사**:
> **"01이 끝나면 02 spec이 그 intent.md를 읽어서 스펙을 씁니다. 03 build는 그 스펙을 읽고 별도 git worktree에서 실제 코드를 짭니다. 여기서 CLAUDE.md, skills, hooks 3층 가드레일이 걸립니다 — 예를 들어 보호된 경로를 건드리거나 승인 안 된 패키지를 설치하려고 하면 hook이 그 자리에서 막습니다."**

**소요**: 2~3분.

### 5) 04 test — 심어둔 버그가 e2e에 걸림 (2분)

**보여주는 것**: 04 test 단계가 pytest/vitest는 통과하지만 ego-lite e2e에서 실패하는 것. 터미널 로그에 실패 원인이 찍히는 것.

**화면**: 러너 로그에 e2e 실패 메시지, zoe에서 04 test 세션이 실패 상태로 마무리되는 것.

**대사**:
> **"이 데모 프로젝트에는 일부러 작은 버그를 심어뒀습니다. 단위 테스트는 통과하지만, 실제 화면에서 값이 하나 어긋나거나 리스트가 비어 보이는 정도의 버그라 e2e에서만 걸립니다. ego-lite가 실제 브라우저에서 화면을 스냅샷 떠서 이걸 잡아냅니다."**

**소요**: 2분(로그가 뜰 때까지 대기 포함).

### 6) 06 maintain — Linear에 새 티켓 자동 생성 (클라이맥스, 1~2분)

**보여주는 것**: 04 실패를 받은 06 maintain이 진단하고 Linear API로 새 티켓을 만드는 순간. Linear 보드를 다시 띄워서 새 카드가 뜨는 걸 실시간으로 보여준다.

**화면**: 러너 로그에 "새 티켓 생성" 메시지 → Linear 보드에 새 카드가 나타남(라벨 `sdlc-auto`).

**대사**:
> **"여기가 오늘 보여드리고 싶었던 지점입니다. 04에서 실패가 나면 06 maintain이 원인을 진단하고, 사람이 티켓을 다시 안 만들어도 Linear에 직접 새 티켓을 만듭니다."**
> (Linear 화면 가리키며) **"지금 막 생긴 이 카드가 그겁니다. `sdlc-auto` 라벨이 붙어서 자동 생성된 티켓이라는 걸 구분할 수 있습니다."**

**소요**: 1~2분. **이 구간은 절대 서두르지 않는다** — 발표의 핵심 메시지가 여기서 완성된다.

### 7) 새 티켓이 01을 재트리거 — 루프가 닫힘 (1분)

**보여주는 것**: 방금 생긴 티켓이 다시 러너로 들어와 01 intent가 시작되는 것을 로그로 짧게 확인.

**화면**: 왼쪽 터미널 로그에 새 티켓 ID로 01 intent가 다시 시작되는 로그.

**대사**:
> **"그리고 이 새 티켓이 다시 01 intent를 트리거합니다. 사람 개입 없이 문제 발견부터 재작업 시작까지 루프가 한 바퀴 닫힌 겁니다. 물론 무한히 도는 건 아니고, 자동 생성 티켓에는 깊이 제한이 걸려 있어서 같은 문제가 계속 반복되면 사람에게 넘어갑니다."**

**소요**: 1분.

### 8) 마무리 (1분)

**대사**:
> **"오늘 본 건 6단계 전체가 자동으로 도는 걸 실시간으로 본 겁니다. 사람은 배포 승인 같은 판단이 필요한 지점에서만 개입합니다. 질문 받겠습니다."**

**소요**: 1분.

## 2. 실패 대비

시연 중 깨질 수 있는 지점과, 그때 즉시 쓸 대체 자료를 미리 준비해둔다.

| 실패 상황 | 즉석 대응 | 미리 준비해둘 것 |
| --- | --- | --- |
| 네트워크가 죽었을 때 | "네트워크 이슈로 라이브 대신 미리 녹화한 걸 보여드리겠습니다"라고 말하고 바로 영상 재생 | 파이프라인 1회 완주 전체를 사전에 화면 녹화해둔다(1)~(7) 전 구간. 발표 노트북에 로컬 파일로 저장, 재생 앱도 미리 열어둔다 |
| Linear webhook이 안 올 때 | 러너에 동일 이벤트를 수동으로 주입해서 흐름을 이어간다 | webhook payload와 동일한 내용을 로컬에서 재현하는 curl/스크립트를 미리 만들어 데스크톱에 준비 |
| ego-lite 온보딩이 안 됐을 때(04 test에서 e2e 자체가 안 뜸) | "환경 문제로 이번엔 결과만 보여드리겠습니다"라며 이미 캡처해둔 실패 로그/스크린샷으로 대체 | 04 test 실패 로그 전문과 스크린샷을 미리 캡처해서 슬라이드나 별도 파일로 준비 |
| `claude -p`가 오래 걸릴 때 | 그 사이 다음에 할 이야기(가드레일, 무한 루프 방지 등)를 먼저 설명하며 시간을 벌거나, 미리 만들어둔 세션 JSONL로 갈아탄다 | 6단계 각각의 세션 JSONL을 사전에 1세트 만들어 백업해두고, 느리면 `zoe <file.jsonl> --speed 8`로 그 파일을 재생해 "라이브처럼" 이어간다 |

공통 원칙: **모든 실패 대응은 "이미 만들어둔 결과물로 전환"이다.** 라이브 데모가 막히는 순간 새로 뭔가를 디버깅하려 하지 않는다. 관객 앞에서 트러블슈팅하지 말고 바로 대체 자료로 넘어간다.

## 3. 질의응답 대비

| 예상 질문 | 답변 요지 |
| --- | --- |
| 에이전트가 프로덕션에 직접 배포하나? | 아니다. 05 deploy는 PR 생성과 리뷰 게이트 hook까지다. 실제 프로덕션 배포·인프라는 이 설계의 범위 밖이고, 사람 승인 이후 별도 절차로 넘어간다. |
| 비용은 얼마나 드나? | 단계마다 `claude -p` 세션 비용이 들지만, 원문 기준 build 단계에서만 2배 속도 향상이 보고됐고 사람 리뷰/워크숍 비용이 줄어드는 걸로 상쇄를 노린다. 정확한 금액은 사용량과 모델 선택에 따라 달라 여기서 고정 수치를 제시하진 않는다. |
| 에이전트가 잘못된 코드를 밀면 어떻게 막나? | hooks가 결정론적으로 막는다 — 보호 경로 편집 차단, 자동 포맷·린트, 자격 증명이 diff에 섞이면 차단, 미승인 패키지 설치 차단, 그리고 05 deploy의 배포 게이트는 exit code 2로 그 자리에서 막는다. CLAUDE.md/skills는 유도일 뿐이고 hooks만 강제한다. |
| 이미 Jira를 쓰는데 Linear로 갈아타야 하나? | 아니다. 트리거 소스는 `TicketSource` 인터페이스(`verify`/`parse`/`createTicket`/`comment`) 하나로 격리돼 있다. `adapters/jira.ts`가 이 인터페이스만 구현하면 드롭인 교체다. 이번 데모는 구현체로 Linear를 썼을 뿐이다. |
| 무한 루프에 안 빠지나? | 06이 만드는 티켓엔 `sdlc-auto` 라벨과 depth 값이 붙는다. depth가 상한을 넘으면 자동 재생성을 멈추고 사람에게 에스컬레이션한다. |
| GitHub Actions를 안 쓰는 이유는? | 실행기를 로컬 러너 하나로 뒀다. CI 러너에서는 `zoe`로 실시간 스트리밍하며 보여주는 게 어렵고, 애초에 요구사항에 CI가 없었다. |
| zoetrope가 Claude Code 업데이트로 깨지면? | zoetrope는 Claude Code의 비공식 내부 JSONL 포맷을 리버스 엔지니어링한 뷰어라 그럴 수 있다. `zoe inspect <session>.jsonl`로 파싱 여부를 먼저 확인하면 된다. 다만 이건 시각화 도구 문제일 뿐 파이프라인 자체(01~06 실행, 아티팩트 생성)는 zoetrope와 무관하게 동작한다. |
